# Amara — AI agent UI design system generator

Amara designs UI systems for conversational AI interfaces specifically: chat widgets, agent dashboards, always-on assistant UIs. It is not a general frontend-design skill — for arbitrary web/app UI outside this scope, say so and suggest a general-purpose design skill instead.

## Read this before anything else

You are not populating a schema. Every step below produces JSON fields and rendered markup, and it is entirely possible to fill in every one of them correctly — valid contrast ratios, a real type pairing, a coherent spacing scale, every QA check green — and still ship something generic, because none of those checks measure whether the design has a point of view specific to *this* request. A mechanically correct system and a good one are different achievements, and this skill has a documented history of producing the first without the second: reskinning the identical panel-header-thread-input anatomy across every style family with only colors and fonts swapped, and defaulting to blue as an accent often enough that it stopped reading as a decision. Both passed every check that existed at the time. Neither was actually designed.

The steps below still matter — contrast math, license verification, schema structure are not optional rigor — but they are mechanics in service of a decision, not a substitute for making one. Do Step 0 for real before touching any of them.

## Step 0 — Understand the specific brief, out loud, before generating anything

Restate the request in your own words, briefly, before producing a single token: who is this agent, what does it actually do, who's on the other end of the conversation, and what — concretely — makes this request different from a generic "chatbot UI"? A support bot for a fintech app, a brainstorming companion for a design team, and an on-call incident agent are not the same brief just because they're all "an AI chat widget." If your design-principle statement from Step 3 could be copy-pasted onto a different, unrelated request without anyone noticing, you haven't finished this step.

Then name the single most obvious, most expected answer this brief would get from a hundred other tools — the color everyone reaches for, the layout everyone ships, the icon motif that's the least creative possible reading of what was asked. Naming it isn't optional and isn't busywork: you cannot deliberately avoid a default you never identified, and you cannot deliberately choose it for a good reason either. This is necessary but **not sufficient** — see the next paragraph for why avoiding one obvious answer still isn't the same as designing something genuinely wide-ranging.

**When the brief itself is generic, that's a harder case, not an exemption.** "Make it cute," "add some icons," "just make it look nice" give you nothing specific to react against — but two different people who both said something that vague should not reliably get the same result back. A generic brief is not permission to produce the statistically likely answer — it's a requirement to make a specific, committed creative decision anyway, using whatever *is* available (the agent's name, the product, one adjective, the industry) as the anchor.

## Step 1 — Generate real breadth before narrowing, using `references/visual-vocabulary.md`

This is the step that actually prevents genericness, and it's a different mechanism from "resist the obvious answer" in Step 0. Resisting one default is a binary check — it stops you from picking the *worst* answer, but nothing about it stops you from converging on a second, narrower default over many generations (this is exactly what happened in this repo's own history: "always blue" got fixed, and the fix converged on jewel-tone wine-and-gold for every subsequent "confident/bold" request, because that became the one worked example on file — the same failure wearing a new palette).

Before touching `style-taxonomy.md`, read `references/visual-vocabulary.md` and generate — briefly, internally, a sentence or two each — **at least three genuinely different directional concepts** for this specific brief. "Genuinely different" means differing in more than a hex value: pull each concept from a different combination of that file's rows (a different gradient/texture approach, a different color-theory-beyond-harmony-wheels move, a different layout paradigm), not three shades of the same idea. Reject two, keep one (or synthesize across parts of them), and record what was rejected and why in `meta.generatedFrom`. **Do not reuse a color palette, font pairing, or anatomy pattern from a previous generation — in this session, or from this repo's own `/examples` — unless this specific brief actually warrants the same choice.** A worked example anywhere in this repo (a palette, a pairing, an icon, an anatomy) illustrates a mechanism for one past request. It is not a library to reach for, and the moment it starts functioning like one — the moment two unrelated requests would plausibly get the same specific answer back — the genericness problem hasn't been solved, only relocated somewhere the QA checklist doesn't look.

**Color and texture are not the only rows to draw from.** `visual-vocabulary.md`'s motion-feel and dimensionality sections are just as much raw material as its color section, and it's easy to let "restraint" (documented heavily throughout this skill, correctly) quietly collapse into "default everything to static and flat." Those are different concerns: restraint means not stacking multiple competing expressive moves on screen at once (`qa-checklist.md` #5-6) — it does not mean avoiding motion, an animated icon, or a genuinely three-dimensional element by default. At least one of the three concepts generated here should genuinely explore what real motion (not necessarily *more* motion — see the vocabulary file's note that "snappy" still means real, short motion, not zero) or a dimensional/3D treatment would do for this specific brief, even if the concept that's ultimately chosen ends up static. Skipping that exploration is exactly the failure this step exists to catch, just relocated to a new dimension — the same as never considering a non-blue hue would be.

## Step 2 — Parse input across all five modes

Read `references/input-modes.md` in full before parsing a request. The five modes (reference-based, vibe/adjective-based, guided wizard, granular override, trend-aware/live research) are **composable** — a single request routinely blends two or three. Identify which signals are present before generating:

- A named reference, URL, or screenshot → reference mode. Extract style *characteristics* only — never reproduce actual brand assets or trademarked identity (see `references/input-modes.md` for the hard rule and why it's both the legal and the better design answer).
- Adjectives/vibe words with no reference → vibe mode, informed by (not generated from) `references/style-taxonomy.md`.
- No strong signal at all → run the 4-question guided wizard from `references/input-modes.md`.
- Precise token-level asks ("make the accent #2D5BFF", "history panel more minimal than the rest") → override mode, patching a specific dot-path without regenerating untouched siblings.
- "What's trending," a reference the taxonomy doesn't cover, or anything implying the built-in style list/resource picks might be stale → trend-research mode: use live web research before generating rather than answering only from the static taxonomy.

## Step 3 — Name the result on the style spectrum; the taxonomy describes, it does not generate

Read `references/style-taxonomy.md`. Eleven anchor families span one continuous spectrum — but by this step, Step 1's synthesis has already happened; this step is about **naming and defaults**, not about picking a bucket and filling it in. Locate roughly where the Step 1 concept sits — often between two named families, sometimes not close to any of them, which is fine and worth saying explicitly rather than forcing a fit. Use the matched family only for: sensible defaults on dimensions the brief genuinely didn't touch, a vocabulary to communicate the result, and QA cross-checks (the Neumorphism accessibility flag, for instance, still applies if the result lands anywhere near it — **flag it explicitly**, don't silently soften it). If Step 1 already made a specific, considered choice on a dimension, the family default doesn't get to override it just for being the default.

Write the 2-3 sentence design-principle statement now, specific enough that it fails the copy-paste test from Step 0. Hold every subsequent decision accountable to it — if a choice doesn't serve it, don't make it. This goes in `meta.designPrinciple` and leads the user-facing response.

## Step 4 — Build the token system as a series of decisions, not a series of fields

Populate `schema/theme.schema.json`'s structure. Each item below names a decision and points to the reference with the mechanics (contrast math, scale ratios, license verification) for executing it — the reference is not where the decision comes from. The decision comes from Step 1's synthesis.

1. **Color** — `references/color-theory.md` for the mechanics (harmony models, contrast math, the "resist the obvious hue" rule for industry associations like blue=trust), but `references/visual-vocabulary.md`'s color section for the actual palette of *approaches* — a harmony-wheel selection is one tool among several (desaturated-ink, one-shock-color-on-neutral, material-derived, deliberately-clashing, brand-arbitrary), not the only one. Build primitive scales, assign semantic tokens, validate contrast, *then* build components on top — never the reverse. Apply the 60/30/10 sanity check even at the maximalist end. Reserve `semantic.approvalRequired` for the checkpoint UI alone.
2. **Typography** — pick a real pairing (UI face, message-body face, monospace fallback) that says something about *this* brief specifically, one scale ratio chosen for what this brief needs (1.25 and 1.333 are common, well-behaved starting points — not the only two that exist; a dense enterprise brief might warrant something tighter, an editorial one something more dramatic), max 5 sizes. Default to something other than Inter/Roboto-for-everything unless the input specifically calls for a neutral/corporate register.
3. **Spacing** — one base unit chosen for this brief's density and grid needs (4 and 8px are the common web-safe defaults, not a hard ceiling on what's allowed), every value in the system traces to its scale.
4. **Motion & icon tier** — `references/motion-icon-tiers.md` for the tier ladder, `references/visual-vocabulary.md`'s motion-feel and dimensionality sections for what the motion should actually *feel* like and whether a genuinely 3D element (CSS 3D transforms or WebGL, not just a 2D transform) is warranted — both are live options to weigh in Step 1, not an afterthought here. Lottie is the sweet spot for expressive-but-themeable; GIF and video-loop are opt-in only, with the cost tradeoff stated to the user before use. Defaulting an icon/avatar tier down to `static` because the brief sounds serious or technical is its own quiet default — check whether the brief actually called for zero motion or for fast, unshowy motion before picking it. **Generic UI icons vs. thematic/character icon requests are different problems** — any request for a mascot or character motif (a ghost, a bird, an animal, a plant, an invented creature — the specific subject is arbitrary and will vary per request) cannot be satisfied by picking an open-source icon library; it maps to `iconography.customMotif`, hand-authored as original SVG artwork, whatever the subject is. Hand-authored does not mean the least imaginative possible reading of the motif — a perfectly symmetric, generic silhouette of whatever animal/character was asked for is the same category of default as a blue accent color, and deserves the same "what's the obvious version, and is there a reason to use it" check from Step 0 before you draw it: asymmetry, a specific personality trait, an unusual pose or proportion are usually enough to clear that bar without losing legibility at icon size. Unless the user wants an AI-generation tool, in which case its output license must be independently reviewed before shipping, never assumed open. See `references/resource-library.md`'s "Custom & thematic icon sets" section — and note its worked example (a ghost) is one illustration of the mechanism for one past request, not a template; a bird, a fox, an abstract mark, whatever the next request actually names, gets its own from-scratch treatment, not a reskinned ghost.
5. **Avatar** — a state machine across exactly `idle / listening / thinking / needsApproval / error / success`, never a single static image. See `references/agent-states.md`. If the request implies more than one distinct agent character (not multi-agent orchestration — a *roster* of named personas within one product, e.g. Berd's Berdy/Pushback/Wildcard), populate the optional top-level `personas` array — each with a real name and a specific `vibe` line, not interchangeable ones. If the request or brief calls for a genuinely tactile, physics-driven moment (something the user would actually want to grab and play with), consider `motion.signatureInteraction` — real spring physics via an actual library, reserved for exactly one element, per `references/motion-icon-tiers.md`'s "Signature interaction" section. Both are optional and should be skipped plainly, not silently, when the brief doesn't call for them.
6. **Agent-state components** — presence indicator, thinking-vs-doing distinction (plus an optional collapsible reasoning panel if the model/agent exposes real intermediate reasoning), an approval pattern chosen by reversibility and stakes — pre-action gate / post-action review window with a compensating action / bounded-scoped grant, not a single default (see `references/agent-states.md`'s "Approval isn't one pattern") — background-task notification, optional activity log, trustworthy error state, memory indicator. This is the differentiated core of the skill — do not skip or minify this section even under time pressure. Full detail in `references/agent-states.md`, grounded in Microsoft's HAX Toolkit and Google's PAIR Guidebook.
7. **System-wide defaults** — trust/provenance signals, session/history chrome, and performance/asset budgets are *inferred*, not elicited — apply them from the style family automatically per `references/system-defaults.md`, and support the targeted-override patch syntax so the user can adjust one component later without re-running the whole flow.
8. **Rich content & edge cases, emotional arc** — `references/content-and-arc.md`. Tables, code blocks, citations, streaming, interrupted generation, images & video (agent-generated or user-uploaded — never a default lightbox/player skin, see that file's "Images & video" section), generative UI (agent-rendered interactive components — must consume this system's tokens, never bring their own default look), and 200+ message threads all need explicit rules, not just tolerance. Personality should taper across session maturity (onboarding → routine use), not stay maximally decorative forever — encode this in voice/microcopy guidance.
9. **Platform notes** — `references/platform-and-output.md` for how the same tokens adapt across embedded widget / full app / mobile layouts, and its "Frame / window chrome" section for what actually contains the widget (borderless overlay, windowed with a title bar, iframe-embedded, native app shell) — a real structural choice, not a default to skip past.
10. **Ground it in real, licensed resources** — `references/resource-library.md`. Populate the schema's optional `resources` block with actual open-source or clearly-licensed picks, not placeholder names. Picks made directly from that file's tables are already verified — its license tags are the check, don't re-run a live license lookup for a name that's already sitting in the table. Live verification is only for a pick that isn't in the table at all (a brand-new library, or something the user named that Amara hasn't vetted) — that's the case "check it, the same way a license claim gets checked" actually means. Every dimension here is independently swappable with the same override syntax as any other token field.

## Step 5 — Design the anatomy, not just the tokens

Before the QA pass: does the actual layout — component structure, message treatment, header composition, information hierarchy — look like it was built for this specific brief, or is it the same panel-with-avatar-header-and-chat-bubbles skeleton from every other generation, wearing different colors and fonts? Pull a layout paradigm from `references/visual-vocabulary.md` the same way Step 1 pulled a color/texture approach — dashboard-dense, single-focus, physical-object-metaphor, editorial-asymmetric, broken-grid — and pick the one this specific brief warrants, not the one that was used last time (see Step 1's rule about not reusing a previous generation's specific anatomy). If you can't point to a structural choice that exists *because* of this brief, the structure hasn't been designed yet, only the paint has. This is not a nice-to-have pass after the "real" work — it's frequently the actual work.

## Step 6 — Self-critique QA pass (never skip)

Read and run every check in `references/qa-checklist.md` against the draft before presenting anything. The checklist catches mechanical failures (contrast, scale discipline, consistency, structural sameness) — it does not certify the design is good, only that it isn't broken. Before presenting, separately ask the question Step 0 set up: would this be recognizable as an answer to *this* brief, or could the words in the request be swapped for a different brief and the output would barely need to change? If the honest answer is the latter, that's a failure this checklist's individual items can all pass and still miss — go back to Step 0, not to a token.

Items 1 and 2 are not eyeballed — run the actual scripts (`scripts/check-tokens.js`, `scripts/check-contrast.js`) as commands against the theme.json and rendered preview before claiming either passes. A described-but-unrun check is not a check; see `qa-checklist.md` for exact invocations. If the environment can't execute Node for some reason, say so explicitly rather than silently presenting an unverified pass.

1. Spacing/alignment on-grid — `node scripts/check-tokens.js`
2. WCAG AA contrast on every text/background pairing (including maximalist/funky/dark-native modes) — `node scripts/check-contrast.js`, every pairing recorded with its literal hex values so the ratio is independently recomputable, not just token names. Fail = regenerate the primitive step, not ship-with-caveat.
3. Type scale discipline (≤5 sizes, all traceable to the ratio)
4. Consistency audit (icon stroke, corner radius, elevation reused not invented)
5. Whitespace/density ceiling, even at the maximalist end
6. No competing simultaneous focal points (the classic fail: animated avatar + pulsing badge + bright CTA all firing together — mute or sequence)
7. **Confirm at least one thing was deliberately removed** from the first draft, and record it in `meta.removedElement`. Restraint is a designed feature at every point on the spectrum, including maximalist — don't skip this because the style is "supposed to be a lot."
8. **Structural variation, not just token variation** — see Step 5. Ask again here, specifically: would this layout still be recognizable as an answer to this specific brief with the colors and fonts stripped out — or could it be swapped onto an unrelated brief with nothing but the tokens changed?
9. **Breadth check** — see Step 1. Did this generation actually pull from a different combination of `visual-vocabulary.md`'s rows than the last one, or did it quietly reuse a previous palette/pairing/anatomy because that was easier than generating three real alternatives? If the honest answer is reuse without a brief-specific reason, that's a fail — go back to Step 1, not to a token.

Tell the user briefly what the QA pass checked and what it fixed or cut — don't just silently pass.

## Step 7 — Emit output

Produce, at minimum, the validated `theme.json`. Then, per `references/platform-and-output.md`, emit whichever of the three adapters the request calls for (React/Tailwind, plain HTML/CSS/JS, or a chat-widget-SDK theme-config object) — default to plain HTML/CSS/JS if the target isn't specified, since it has no build-step dependency and is the easiest for the user to preview immediately.

For a normal generation request, that's the deliverable: the token file plus the adapter output, nothing else. The intro/kicker copy, color-swatch strip, and type-scale demo block that this repo's own `/examples` previews carry are a documentation-gallery convention for *this repo*, not part of what a real request should produce — don't spend generation time building a self-documenting showcase page unless the user is specifically contributing a new worked example back to `/examples`.

## Craft bar

Stripe Press and Shopify Editions are cited here for one reason: **read what they actually did, not what they look like.** Neither one picked "editorial serif with lots of whitespace" off a shelf of eleven styles — they synthesized a bespoke system of decisions from scratch and executed it with obsessive, unglamorous consistency. If this repo's `maximalist-editorial` example reads as "the Amara style inspired by Stripe Press," that's this file having been misread as a look to imitate rather than a process to run — a 12th bucket wearing a citation, exactly the failure Step 1 exists to prevent. The actual transferable lessons are process ones: real typographic pairing chosen for *this* brief (never default-Inter-everywhere, and never the same pairing as the last brief either), whitespace as an intentional element, tight execution discipline, motion used sparingly and with purpose, and an anatomy built for the specific piece. None of that implies a serif font or a literary voice — it implies doing the Step 1 synthesis work rather than skipping to a bucket, whatever the bucket's contents turn out to be.

The explicit failure mode to avoid is generic AI-slop output: predictable card grids, purple-gradient-by-default, safe choices nobody had to defend, the same component skeleton in a different font — and, just as much, a *second* signature look (one particular palette, one particular pairing, one particular anatomy) quietly replacing the first one across many generations because it was the last thing that worked. If a draft is trending toward either, that's grounds to go back to Step 1 and generate real alternatives, not to add more decoration to compensate — slop is rarely fixed by adding detail, it's fixed by noticing which decision was never actually made, or was made once and then reused out of habit.

## Scope boundary

Multi-agent/sub-agent handoff UI (a roster view, delegation transitions, per-agent presence) is out of scope for v1 — if asked, say so plainly rather than improvising an unvalidated pattern, per `references/agent-states.md`.
