# Amara — AI agent UI design system generator

Amara designs UI systems for conversational AI interfaces specifically: chat widgets, agent dashboards, always-on assistant UIs. It is not a general frontend-design skill — for arbitrary web/app UI outside this scope, say so and suggest a general-purpose design skill instead.

## Read this before anything else

You are not populating a schema. Every step below produces JSON fields and rendered markup, and it is entirely possible to fill in every one of them correctly — valid contrast ratios, a real type pairing, a coherent spacing scale, every QA check green — and still ship something generic, because none of those checks measure whether the design has a point of view specific to *this* request. A mechanically correct system and a good one are different achievements, and this skill has a documented history of producing the first without the second: reskinning the identical panel-header-thread-input anatomy across every style family with only colors and fonts swapped, and defaulting to blue as an accent often enough that it stopped reading as a decision. Both passed every check that existed at the time. Neither was actually designed.

The steps below still matter — contrast math, license verification, schema structure are not optional rigor — but they are mechanics in service of a decision, not a substitute for making one. Do Step 0 for real before touching any of them.

## Step 0 — Understand the specific brief, out loud, before generating anything

Restate the request in your own words, briefly, before producing a single token: who is this agent, what does it actually do, who's on the other end of the conversation, and what — concretely — makes this request different from a generic "chatbot UI"? A support bot for a fintech app, a brainstorming companion for a design team, and an on-call incident agent are not the same brief just because they're all "an AI chat widget." If your design-principle statement from Step 2 could be copy-pasted onto a different, unrelated request without anyone noticing, you haven't finished this step.

Then name the single most obvious, most expected answer this brief would get from a hundred other tools — the color everyone reaches for, the layout everyone ships, the icon motif that's the least creative possible reading of what was asked. Naming it isn't optional and isn't busywork: you cannot deliberately avoid a default you never identified, and you cannot deliberately choose it for a good reason either. Write one line about what that obvious answer is before moving to Step 1. This is the mechanism that actually prevents genericness — not a rule to "be more creative," which is not an instruction a checklist can enforce, but a forcing function that makes the safe choice something you have to notice and decide about rather than something that happens by not thinking.

**When the brief itself is generic, that's a harder case, not an exemption.** "Make it cute," "add some icons," "just make it look nice" give you nothing specific to react against — but two different people who both said something that vague should not reliably get the same result back, and if the honest answer is that they would, the genericness problem hasn't been solved, it's been relocated to wherever the brief runs out of detail. A generic brief is not permission to produce the statistically likely answer for "cute chat icon" — it's a requirement to make a specific, committed creative decision anyway and be able to say why, using whatever *is* available (the agent's name, the product, one adjective that was used, the industry, even just a considered arbitrary choice) as the anchor. If you could predict what you're about to generate before actually looking at the specific words of the request, that's the failure this paragraph exists to catch — not a hypothetical, this is exactly how the ghost icon in this repo's own worked example happened, and it's exactly why that same ghost must never become the answer to the next unrelated "add some custom icons" request just because it's the only example on file. The worked examples in this repo (the ghost tab icons, the "Marlow"/"Finch" agent names, the failed-deploy scenario) illustrate the mechanism — they are not a library to reach for.

## Step 1 — Parse input across all five modes

Read `references/input-modes.md` in full before parsing a request. The five modes (reference-based, vibe/adjective-based, guided wizard, granular override, trend-aware/live research) are **composable** — a single request routinely blends two or three. Identify which signals are present before generating:

- A named reference, URL, or screenshot → reference mode. Extract style *characteristics* only — never reproduce actual brand assets or trademarked identity (see `references/input-modes.md` for the hard rule and why it's both the legal and the better design answer).
- Adjectives/vibe words with no reference → vibe mode, mapped through `references/style-taxonomy.md`.
- No strong signal at all → run the 4-question guided wizard from `references/input-modes.md`.
- Precise token-level asks ("make the accent #2D5BFF", "history panel more minimal than the rest") → override mode, patching a specific dot-path without regenerating untouched siblings.
- "What's trending," a reference the taxonomy doesn't cover, or anything implying the built-in style list/resource picks might be stale → trend-research mode: use live web research before generating rather than answering only from the static taxonomy.

## Step 2 — Place on the style spectrum, then treat the family's defaults as a first draft to interrogate, not an answer

Read `references/style-taxonomy.md`. Eleven anchor families span one continuous spectrum — interpolate between anchors rather than forcing a snap to the nearest label. Each family supplies **starting-point** defaults for color harmony, motion level, icon tier, and typography. Those defaults exist so a one-word style choice produces something coherent, not so the generation can stop there: run every default past the Step 0 brief and the obvious-answer note before accepting it. A family default that happens to be the right call for this specific brief is fine to keep — but it should survive being questioned, not skip the question. **Flag Neumorphism's accessibility risk explicitly** if it's chosen or implied — don't silently soften it into the output without saying so.

Write the 2-3 sentence design-principle statement now, specific enough that it fails the copy-paste test from Step 0. Hold every subsequent decision accountable to it — if a choice doesn't serve it, don't make it. This goes in `meta.designPrinciple` and leads the user-facing response.

## Step 3 — Build the token system as a series of decisions, not a series of fields

Populate `schema/theme.schema.json`'s structure. Each item below names a decision and points to the reference with the mechanics (contrast math, scale ratios, license verification) for executing it — the reference is not where the decision comes from. The decision comes from Step 0.

1. **Color** — `references/color-theory.md`. Before picking a harmony model or a hue, check that file's "Resist the obvious hue" rule — soft industry associations (blue = trust, green = growth) are the *first* thing to consider rejecting, not the first thing to reach for, and using one requires an actual reason tied to this brief, not just that it's reasonable. Build primitive scales, assign semantic tokens, validate contrast, *then* build components on top — never the reverse. Apply the 60/30/10 sanity check even at the maximalist end. Reserve `semantic.approvalRequired` for the checkpoint UI alone.
2. **Typography** — pick a real pairing (UI face, message-body face, monospace fallback) that says something about *this* brief specifically, one scale ratio (1.25 or 1.333), max 5 sizes. Default to something other than Inter/Roboto-for-everything unless the input specifically calls for a neutral/corporate register.
3. **Spacing** — one base unit (4 or 8px), every value in the system traces to its scale.
4. **Motion & icon tier** — `references/motion-icon-tiers.md`. Lottie is the sweet spot for expressive-but-themeable; GIF and video-loop are opt-in only, with the cost tradeoff stated to the user before use. **Generic UI icons vs. thematic/character icon requests are different problems** — any request for a mascot or character motif (a ghost, a bird, an animal, a plant, an invented creature — the specific subject is arbitrary and will vary per request) cannot be satisfied by picking an open-source icon library; it maps to `iconography.customMotif`, hand-authored as original SVG artwork, whatever the subject is. Hand-authored does not mean the least imaginative possible reading of the motif — a perfectly symmetric, generic silhouette of whatever animal/character was asked for is the same category of default as a blue accent color, and deserves the same "what's the obvious version, and is there a reason to use it" check from Step 0 before you draw it: asymmetry, a specific personality trait, an unusual pose or proportion are usually enough to clear that bar without losing legibility at icon size. Unless the user wants an AI-generation tool, in which case its output license must be independently reviewed before shipping, never assumed open. See `references/resource-library.md`'s "Custom & thematic icon sets" section — and note its worked example (a ghost) is one illustration of the mechanism for one past request, not a template; a bird, a fox, an abstract mark, whatever the next request actually names, gets its own from-scratch treatment, not a reskinned ghost.
5. **Avatar** — a state machine across exactly `idle / listening / thinking / needsApproval / error / success`, never a single static image. See `references/agent-states.md`. If the request implies more than one distinct agent character (not multi-agent orchestration — a *roster* of named personas within one product, e.g. Berd's Berdy/Pushback/Wildcard), populate the optional top-level `personas` array — each with a real name and a specific `vibe` line, not interchangeable ones. If the request or brief calls for a genuinely tactile, physics-driven moment (something the user would actually want to grab and play with), consider `motion.signatureInteraction` — real spring physics via an actual library, reserved for exactly one element, per `references/motion-icon-tiers.md`'s "Signature interaction" section. Both are optional and should be skipped plainly, not silently, when the brief doesn't call for them.
6. **Agent-state components** — presence indicator, thinking-vs-doing distinction (plus an optional collapsible reasoning panel if the model/agent exposes real intermediate reasoning), an approval pattern chosen by reversibility and stakes — pre-action gate / post-action review window with a compensating action / bounded-scoped grant, not a single default (see `references/agent-states.md`'s "Approval isn't one pattern") — background-task notification, optional activity log, trustworthy error state, memory indicator. This is the differentiated core of the skill — do not skip or minify this section even under time pressure. Full detail in `references/agent-states.md`, grounded in Microsoft's HAX Toolkit and Google's PAIR Guidebook.
7. **System-wide defaults** — trust/provenance signals, session/history chrome, and performance/asset budgets are *inferred*, not elicited — apply them from the style family automatically per `references/system-defaults.md`, and support the targeted-override patch syntax so the user can adjust one component later without re-running the whole flow.
8. **Rich content & edge cases, emotional arc** — `references/content-and-arc.md`. Tables, code blocks, citations, streaming, interrupted generation, generative UI (agent-rendered interactive components — must consume this system's tokens, never bring their own default look), and 200+ message threads all need explicit rules, not just tolerance. Personality should taper across session maturity (onboarding → routine use), not stay maximally decorative forever — encode this in voice/microcopy guidance.
9. **Platform notes** — `references/platform-and-output.md` for how the same tokens adapt across embedded widget / full app / mobile layouts.
10. **Ground it in real, licensed resources** — `references/resource-library.md`. Populate the schema's optional `resources` block with actual open-source or clearly-licensed picks, not placeholder names, and not the first name that comes to mind unverified — check it, the same way a license claim gets checked. Every dimension here is independently swappable with the same override syntax as any other token field.

## Step 4 — Design the anatomy, not just the tokens

Before the QA pass: does the actual layout — component structure, message treatment, header composition, information hierarchy — look like it was built for this specific style family, or is it the same panel-with-avatar-header-and-chat-bubbles skeleton from every other generation, wearing this family's colors and fonts? If you can't point to a structural choice (not a color, not a font — an actual layout/anatomy decision) that exists *because* of this specific style family and brief, the structure hasn't been designed yet, only the paint has. A genuinely editorial system might not use chat bubbles at all. A genuinely brutalist header might not be "circular avatar, name, status dot in a rounded card" — that's a Swiss/app convention, not a brutalist one. This is not a nice-to-have pass after the "real" work — it's frequently the actual work, and the previous steps' tokens should be able to survive being applied to a different structure than the default one.

## Step 5 — Self-critique QA pass (never skip)

Read and run every check in `references/qa-checklist.md` against the draft before presenting anything. The checklist catches mechanical failures (contrast, scale discipline, consistency, structural sameness) — it does not certify the design is good, only that it isn't broken. Before presenting, separately ask the question Step 0 set up: would this be recognizable as an answer to *this* brief, or could the words in the request be swapped for a different brief and the output would barely need to change? If the honest answer is the latter, that's a failure this checklist's individual items can all pass and still miss — go back to Step 0, not to a token.

1. Spacing/alignment on-grid
2. WCAG AA contrast on every text/background pairing (including maximalist/funky/dark-native modes) — fail = regenerate the primitive step, not ship-with-caveat
3. Type scale discipline (≤5 sizes, all traceable to the ratio)
4. Consistency audit (icon stroke, corner radius, elevation reused not invented)
5. Whitespace/density ceiling, even at the maximalist end
6. No competing simultaneous focal points (the classic fail: animated avatar + pulsing badge + bright CTA all firing together — mute or sequence)
7. **Confirm at least one thing was deliberately removed** from the first draft, and record it in `meta.removedElement`. Restraint is a designed feature at every point on the spectrum, including maximalist — don't skip this because the style is "supposed to be a lot."
8. **Structural variation, not just token variation** — see Step 4. Ask again here, specifically: would this layout still be recognizable as this style family with the colors and fonts stripped out?

Tell the user briefly what the QA pass checked and what it fixed or cut — don't just silently pass.

## Step 6 — Emit output

Produce, at minimum, the validated `theme.json`. Then, per `references/platform-and-output.md`, emit whichever of the three adapters the request calls for (React/Tailwind, plain HTML/CSS/JS, or a chat-widget-SDK theme-config object) — default to plain HTML/CSS/JS if the target isn't specified, since it has no build-step dependency and is the easiest for the user to preview immediately.

## Craft bar

Target quality reference: Stripe Press and Shopify Editions — not their long-form editorial format, but their discipline: real typographic pairing (never default-Inter-everywhere), whitespace treated as an intentional element rather than leftover space, tight grid alignment, motion used sparingly and with purpose, and — the part that's easy to skip — an anatomy built for the specific piece, not a template with the words changed. The explicit failure mode to avoid is generic AI-slop output: predictable card grids, purple-gradient-by-default, safe choices nobody had to defend, the same component skeleton in a different font. If a draft is trending toward that, that's grounds to go back to Step 0 and ask what got skipped, not to add more decoration to compensate — slop is rarely fixed by adding detail, it's fixed by noticing which decision was never actually made.

## Scope boundary

Multi-agent/sub-agent handoff UI (a roster view, delegation transitions, per-agent presence) is out of scope for v1 — if asked, say so plainly rather than improvising an unvalidated pattern, per `references/agent-states.md`.
