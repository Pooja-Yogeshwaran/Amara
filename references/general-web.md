# General-web components — the differentiated core of the general-web branch

This is the general-web branch's counterpart to `agent-states.md`. Where the chat branch's differentiated work is the agent-state machine and approval patterns, this branch's differentiated work is the hero-as-thesis, structure-as-information, and writing components below. Don't skip this section in favor of only shipping tokens — a mechanically correct token system with a generic hero and templated copy is the general-web equivalent of a chat widget with no agent-state components: technically complete, not actually designed.

## Ground it in the subject

If Step 0 didn't pin down what the product or subject is, pin it before designing: name one concrete subject, its audience, and the page's single job. If there's context available about the person's world — their actual work, projects, prior designs — use it as the anchor. The subject's own materials, instruments, artifacts, and vernacular are where distinctive choices come from, not a generic template. Build with the brief's real content and subject matter throughout, not placeholder copy.

## Hero as thesis

Open with the most characteristic thing in the subject's world, in whatever form makes sense for it: a headline, an image, an animation, a live demo, an interactive moment. Be deliberate: a big number with a small label, supporting stats, and a gradient accent is the template answer — only use it if it's genuinely the best option for this subject, not because it's the fastest to build.

## Structure is information

Structural devices — numbering, eyebrows, dividers, labels — should encode something true about the content, not decorate it. Numbered markers (01/02/03) are only appropriate if the content actually is a sequence, like a real process or a timeline where order carries information the reader needs. Question every structural device before incorporating it: does this tell the reader something, or is it just visual rhythm borrowed from another page?

## Typography carries personality

Pair the display and body faces deliberately — not the same families reached for on any other project. Set a clear type scale with intentional weights, widths, and spacing. Make the type treatment itself a memorable part of the design, not a neutral delivery vehicle for the content.

## Motion, deliberately

Think about where and if animation can serve the subject: a page-load sequence, a scroll-triggered reveal, hover micro-interactions, ambient atmosphere. An orchestrated moment usually lands harder than scattered effects. Sometimes less is more — extra animation for its own sake reads as generated rather than designed, the general-web equivalent of stacking a pulsing badge on top of an already-animated avatar.

## Match complexity to the vision

Maximalist directions need elaborate execution; minimal directions need precision in spacing, type, and detail. Elegance is executing the chosen vision well, not adding more to compensate for an under-defined one.

## Writing as design material

Words appear in a design for one reason: to make it easier to understand and use. Bring the same intentionality to copy that you'd bring to spacing and color. Before writing anything, ask what the design needs to say and how to say it in a way that helps the person navigate the experience.

- Write from the end user's side of the screen. Name things by what people control and recognize, not by how the system is built.
- Use active voice as default. An action keeps the same name through the whole flow — a button that says "Publish" produces a message that says "Published."
- Treat failure and emptiness as moments for direction, not mood. Explain what went wrong and how to fix it. An empty screen is an invitation to act, not a dead end.
- Keep the register conversational and tuned to the brief's audience: plain verbs, sentence case, no filler. Let each element do exactly one job — a label labels, an example demonstrates, nothing does double duty.

Generic-sounding copy makes a design feel as templated as generic layout choices do — treat placeholder-sounding copy in a draft the same way Step 6 treats a reused palette: a signal to go back and make an actual decision, not a placeholder to polish later.

## Process note

Work the same brainstorm → explore → plan → critique → build → critique-again loop as Step 1 and Step 6 already require, but apply it specifically to layout and copy here, not just tokens: sketch a layout concept in one-sentence prose plus an ASCII wireframe before writing any code, and hold it against the brief the same way Step 0 holds the design-principle statement — if it reads like the generic default for any similar page, revise it and say what changed and why.

## Restraint

Spend the page's boldness in one place — the signature element from Step 1 — and keep everything around it quiet and disciplined. Not taking a risk can be a risk itself. Build to a quality floor without announcing it: responsive down to mobile, visible keyboard focus, reduced motion respected. Chanel's rule applies here as much as anywhere: before shipping, look at the draft and remove one accessory.
